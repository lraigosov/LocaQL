# Changelog

All notable user-facing changes to LocaQL are documented here, in the style of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). This file is the curated, release-facing summary; `devlog.md` (gitignored, not part of the published repo) is the full internal session-by-session build log this project has kept throughout development — this file distills what actually matters to someone using LocaQL, not the process of building it.

## [0.17.0] - 2026-08-12

### Added
- `cmd/locaql-bench --large-table-rows N` (opt-in, skipped by default) seeds an additional `N`-row table and runs the same `WHERE`+aggregate and `GROUP BY` shapes as the standard 1,000-row workloads, at whatever scale the caller picks — the same reproducible tool now covers the scale the materialized-table cache (`v0.16.0`) targets, not just the small-table baseline. See [`docs/benchmarks.md`](docs/benchmarks.md#caching-materialized-tables-across-queries) for the before/after numbers this produced.

## [0.16.0] - 2026-08-12

### Added
- A read-only query whose referenced tables are all still at the exact catalog version they were last materialized at now skips re-materializing them into the embedded query engine entirely, instead reusing an already-materialized connection — including one a *concurrent* read-only query wanting the identical table set is still using. Every table mutation already bumps a per-table version counter as existing internal bookkeeping, giving an exact, already-correct signal for "safe to reuse" with no new plumbing. External tables, views, session-scoped temp tables and any partition-pruned result are never cached, for correctness reasons specific to each (see `docs/benchmarks.md`); a mutating or session-control statement always keeps its own private, exclusively-owned connection, never a shared one. Cuts a repeated 50k-row query from ~1.2s to ~350ms in this project's own benchmark; see [`docs/benchmarks.md`](docs/benchmarks.md#caching-materialized-tables-across-queries) for the full design, the correctness hazards it was built around (each with a regression test), and a real embedded-engine concurrency bug this surfaced and fixed along the way.

### Fixed
- BigQuery Storage Write's `GetWriteStream` returned `NotFound` for the well-known `_default` stream, because it only resolved streams registered by a prior `CreateWriteStream` call — `_default` is never registered there, since `AppendRows` already resolves it straight against the table's current schema instead. Invisible to a raw `AppendRows` call against `_default`, but it broke the official `cloud.google.com/go/bigquery/storage/managedwriter` client's `DefaultStream` writer outright, since that client calls `GetWriteStream` on `_default` during its own connection-pool setup, before ever appending a row. Found via a real-client benchmarking exercise, not a hand-written test; `GetWriteStream` now resolves `_default` the same way `AppendRows` already did. See `grpc.storage.write` in `capabilities/registry.yaml`.
- Materializing a large table (tens of thousands of rows) into the embedded query engine — done fresh on every query that references it — inserted one row at a time with no explicit transaction, so every row paid its own separate commit; profiling showed this was 74% of total per-query time at 50k rows. Wrapping the existing per-row insert loop in one transaction cut that overhead by roughly 13-16% in repeated benchmark runs. See [`docs/benchmarks.md`](docs/benchmarks.md#materializing-large-tables-a-real-fix-and-a-real-dead-end) for the full profiling data, including a batched-insert approach that was tried, measured, and reverted after it made the same benchmark ~5.5x slower instead of faster.

## [0.15.0] - 2026-08-11

### Added
- Official PHP client conformance: `test/clients/php/persistent_ddl_dml.php`, using `google/cloud-bigquery`, exercises the same persistent SQL mutations (INSERT/UPDATE/MERGE/DELETE/CTAS/DROP) and streaming insert every other client's conformance test already covers, wired into CI as a new `php-client` job — the seventh official client library/CLI now verified against LocaQL. Connects with a minimal `Google\Auth\FetchAuthTokenInterface` implementation returning a literal, never-refreshed fake token (`BigQueryClient`'s `credentialsFetcher` config option accepts this directly — confirmed reading the installed client source, not documentation), the same "fake bearer token nobody validates" approach already used for `bq`/dbt. Passed cleanly on its first real run against every fix the other six clients' conformance testing had already found and closed. See [README: Persistent DDL and DML](README.md#persistent-ddl-and-dml).
- The declarative REST conformance runner (`internal/conformance/runner.go`) now supports a JSON request `body`, `expected_body_contains` substring assertions against the response body, and per-case `setup`/`cleanup` request lists (`cleanup` always runs, even when `setup` or the case itself fails) — previously a case could only issue a bodyless request and check its status code. A new `test/conformance/cases/lifecycle.yaml` exercises datasets/tables create-and-get, table creation with a real schema, a streaming insert followed by a `tabledata.list` read back, and persistent `CREATE OR REPLACE TABLE`/`UPDATE`/`SELECT` through `projects.queries` — all self-contained (each case creates and tears down its own dataset/table) and independent of any one official client library. See [README: Conformance Baseline](README.md#conformance-baseline).
- `ALTER TABLE` now supports `DROP COLUMN [IF EXISTS] name` (one or more, comma-separated; removes the column and the matching cell from every row), `RENAME COLUMN [IF EXISTS] old TO new` (one or more; changes only the schema field's name, never row data), `RENAME TO new_table_name` (moves the table to a new name within the same dataset, keeping schema/rows/partitioning/view identity intact) and `SET OPTIONS(...)` (accepted and its option key/value pairs discarded entirely, the same bounded-scope treatment `CREATE VIEW`'s own `OPTIONS(...)` already gets) — alongside the existing `ADD COLUMN` support, each as its own single-action-per-statement DDL. See [README: Persistent DDL and DML](README.md#persistent-ddl-and-dml) and [Known Divergences](KNOWN-DIVERGENCES.md) for the exact bounded scope (one action kind per statement; no `ALTER COLUMN`).

### Changed
- [Known Divergences](KNOWN-DIVERGENCES.md) Blocking #2 (the query engine's native-Windows/macOS WASM trap) and the [README Requirements](README.md#requirements) section now point to the already-published Docker image (`ghcr.io/lraigosov/locaql`) as the real, existing workaround for *running* LocaQL on those platforms — it runs Linux internally regardless of host OS, so the trap never triggers. Previously only said "none from LocaQL's side today; run through WSL", which undersold a workaround that already shipped as part of this project's own release pipeline. Building/developing the bare `locaql` binary directly on the host is unaffected by this change and still needs WSL on Windows (native macOS has no equivalent built-in Linux layer, so it remains unverified either way for that use case).

## [0.14.0] - 2026-08-11

### Added
- Real Apache Arrow framing for the BigQuery Storage API, on both Read (`CreateReadSession`+`ReadRows`, `DATA_FORMAT_ARROW`) and Write (`AppendRows`, the `arrow_rows` field): `BOOL`/`INT64`/`FLOAT64`/`BYTES`/`STRING`/`DATE`/`DATETIME`/`TIME`/`TIMESTAMP` map to their real, documented BigQuery-to-Arrow types via [`apache/arrow-go`](https://github.com/apache/arrow-go). Verified against the real official `cloud.google.com/go/bigquery` client's `Table.Read()`+`EnableStorageReadClient` path, which always requests `DATA_FORMAT_ARROW` internally — new `test/clients/go/storage_arrow`, wired into CI's `go-client` job. `NUMERIC`/`BIGNUMERIC`/`RECORD`/`REPEATED`/`GEOGRAPHY`/`JSON`/`RANGE` are rejected explicitly rather than downgraded to a string column; `arrow_serialization_options.buffer_compression` is `Unimplemented`. See [README: BigQuery Storage API](README.md#bigquery-storage-api-real-grpc-read-sessions-avroarrow-and-write-streams-protobufarrow) and [Known Divergences](KNOWN-DIVERGENCES.md).
- Real official `dbt-bigquery` adapter conformance: `test/clients/dbt` runs the unmodified `dbt` CLI (`dbt debug`/`dbt run`/`dbt run --full-refresh`) against `view`, `table` (CTAS) and `incremental` (`incremental_strategy='merge'`) models, each executed twice (fresh create, then a real replace/merge), wired into CI as a new `dbt-client` job. Getting there closed five real gaps: persistent DDL/DML target identifiers now accept a backtick around each of `project`/`dataset`/`table` individually (`` `project`.`dataset`.`table` ``, dbt's default DDL quoting style) alongside the pre-existing bare and single-whole-backtick-wrapped forms; `CREATE`/`DROP [MATERIALIZED] VIEW` now execute as real SQL DDL (previously reachable only through `tables.insert`'s `view.query`); `MERGE`'s `USING` clause now accepts a derived table/subquery (`MERGE ... USING (SELECT ...) AS s ON ...`, dbt's default incremental-merge shape) by transparently materializing it into a real ephemeral table before the statement runs; `CREATE SCHEMA [IF NOT EXISTS] dataset_id` is real BigQuery's SQL spelling of dataset creation; and `ALTER TABLE [IF EXISTS] ADD COLUMN [IF NOT EXISTS] name type` (one or more, comma-separated) is real, bounded schema-evolution DDL. See [README: dbt and SQLMesh](README.md#dbt-and-sqlmesh-real-adapterengine-compatibility), [README: Persistent DDL and DML](README.md#persistent-ddl-and-dml) and [Known Divergences](KNOWN-DIVERGENCES.md) for the full account, including SQLMesh's BigQuery engine adapter (config-level connectivity confirmed feasible and its own state-migration DDL now runs; a full `sqlmesh plan`/`run` remains blocked by two issues outside this project's control, documented rather than silently left broken).

### Fixed
- `computeQueryJobResultRows`'s early-poll guard — which exists specifically so a `getQueryResults` poll landing while an async job is still `PENDING`/`RUNNING` never executes that job's mutating statement early or twice — only recognized `INSERT`/`UPDATE`/`DELETE`/`MERGE`/`TRUNCATE`/`CREATE TABLE`/`DROP TABLE`. `CREATE`/`DROP VIEW`, `CREATE SCHEMA` and `ALTER TABLE ADD COLUMN` were missing from it, so a poll landing during the job's real execution window could re-run one of those statements a second time, racing the job's own run over the same catalog version — found via dbt-bigquery conformance testing above (dbt's default `view` materialization hit this on its very first run). All four are now recognized by the same guard.
- `DROP TABLE` now rejects a view target explicitly (`"... is a view; use DROP VIEW"`) instead of deleting it — a real gap surfaced while adding unit coverage for the new `CREATE`/`DROP VIEW` DDL above; `DROP VIEW`/`DROP MATERIALIZED VIEW` remain the correct way to remove one.

## [0.13.0] - 2026-08-09

### Added
- Soak testing for the restart-loop mitigations shipped in `v0.12.0`: `cmd/locaql-bench --soak-duration` sustains load indefinitely (concurrent workers against `SELECT 1 AS one`, no dataset/table dependency) and tracks outage shape — how many distinct continuous-failure periods occurred and how long the longest one lasted — rather than just an error count, failing only if the server stays down longer than `--soak-max-outage` (default 60s). `.github/workflows/soak-test.yml` (manual `workflow_dispatch`, default 20 minutes) runs it against a `locaql start --self-restart` process and uploads the report/log as artifacts, closing the "validate the restart loop over many cycles" follow-up from `v0.12.0`. See [Known Divergences](KNOWN-DIVERGENCES.md) Blocking #3 and [`docs/benchmarks.md`](docs/benchmarks.md#soak-testing-the-restart-loop).
- Official Node.js client conformance: `test/clients/node/persistent_ddl_dml.js`, pinning `@google-cloud/bigquery 8.3.1`, exercises the same persistent SQL mutations (INSERT/UPDATE/MERGE/DELETE/CTAS/DROP) the Python conformance suite already covers, plus a streaming insert against the resulting table, wired into CI as a new `node-client` job. See [README: Persistent DDL and DML](README.md#persistent-ddl-and-dml).
- Official Go client conformance: `test/clients/go/persistent_ddl_dml.go`, using `cloud.google.com/go/bigquery`, exercises the same mutations plus a streaming insert via the client's `Inserter`, wired into CI as a new `go-client` job.
- Official Java client conformance: `test/clients/java` (Maven project), using `com.google.cloud:google-cloud-bigquery`, exercises the same mutations plus a streaming insert via the client's `insertAll`, wired into CI as a new `java-client` job.
- A real BigQuery Discovery API document at `GET /$discovery/rest?version=v2` (`internal/server/discovery.go`), hand-written and deliberately scoped to the `jobs.*` resource (insert/get/list/query/getQueryResults/cancel) rather than bundling Google's full ~570KB document — required for the official `bq` CLI to work at all, since (unlike every other official client library) `bq` fetches this document before issuing any real API call. Makes `bq query` (including real persistent DDL/DML, `test/clients/bq/persistent_ddl_dml.sh`), `bq show -j`, `bq cancel` and `bq ls -j` work against LocaQL, wired into CI as a new `bq-client` job. See [README: bq CLI](README.md#bq-cli-a-hand-written-discovery-document) and `rest.discovery_document` in `capabilities/registry.yaml` for the exact scope.
- Official Ruby client conformance: `test/clients/ruby/persistent_ddl_dml.rb`, pinning `google-cloud-bigquery 1.64.0`, exercises the same persistent SQL mutations plus a streaming insert via the client's `Table#insert`, wired into CI as a new `ruby-client` job. Connects with an anonymous-credentials subclass rather than a real keyfile, mirroring the Go/Java clients' no-auth mode. See [README: Persistent DDL and DML](README.md#persistent-ddl-and-dml).
- Query and script jobs now populate `configuration.query.destinationTable`, matching real BigQuery's own behavior of always assigning a destination table (user-specified or anonymous) to every query job. LocaQL still never materializes query results as a real `project:dataset.table` row set; `tabledata.list` against the new anonymous destination table resolves straight back to the job's own result set instead. See `rest.jobs.query.anonymous_destination_table` in `capabilities/registry.yaml` and [Known Divergences](KNOWN-DIVERGENCES.md) for the exact scope.

### Fixed
- `jobs.insert` now honors a client-supplied `jobReference.jobId` instead of always assigning its own — a real gap found by the new Node.js conformance test above (its official client generates a job ID client-side and polls using that exact value, which LocaQL silently substituted, breaking the poll with a "job not found"). A supplied ID is validated against BigQuery's own character rules and used exactly if free; an invalid ID is rejected with `400`, a collision with an existing job with `409 Already Exists`. See [Known Divergences](KNOWN-DIVERGENCES.md) for the full write-up.
- Job statistics (`totalSlotMs`, `processedBytes`, `outputRows`, and their `statistics.load` equivalents) are now rendered as JSON strings, matching real BigQuery's int64-as-string wire convention — a gap found by the new Go client conformance test above (its generated structs reject an unquoted number for these fields outright, unlike Python's/Node's more lenient parsing).
- Table/query result schema fields now render their `type` using BigQuery's REST wire names (`INTEGER`, `BOOLEAN`, `RECORD`) instead of the GoogleSQL names (`INT64`, `BOOL`, `STRUCT`) used internally — another gap the same Go client conformance test caught: its row-value decoder didn't recognize the GoogleSQL alias, even though its schema parser did. `INFORMATION_SCHEMA.COLUMNS.data_type` is unaffected (real BigQuery uses GoogleSQL names there specifically).
- A job resource now echoes back the submitted query text in `configuration.query.query` — previously always empty, which crashed the official Java client outright (`NullPointerException` reconstructing a `Job` from the `jobs.insert` response) the first time the new Java conformance test above ran.
- A request sent with `Content-Encoding: gzip` is now transparently decompressed before any handler reads it — previously the raw compressed bytes failed to parse as JSON and were silently treated as an empty body, so a `jobs.insert` from a client that compresses its requests (the official Java client does, above a size threshold) created a job with an empty query and a fake simulated result instead of running the real statement or failing loudly. The most consequential of the four conformance gaps this round of multi-client testing found — fixed centrally with one new middleware rather than per-handler.
- `tabledata.list` against a query job's new anonymous destination table (see Added above) no longer silently truncates to 2 rows when a client omits `maxResults` — a real gap found by the new Ruby conformance test above, whose official client's result-fetching path (unlike Python/Node.js/Go/Java, which poll `jobs.getQueryResults`) reads results through exactly this endpoint and, like real BigQuery's own client convention, never sets `maxResults` itself. The anonymous-table path now defaults to the same page size `jobs.getQueryResults` already uses (20, capped at 1000); `tabledata.list` against a real table is unaffected.

## [0.12.0] - 2026-08-09

### Added
- [`SECURITY.md`](SECURITY.md): supported versions, scope, and how to report a vulnerability privately via GitHub Security Advisories.
- `govulncheck` in CI (`vulnerability-scan` job) and `make vuln`, run in `-scan package` mode rather than the default `-scan symbol` due to a confirmed upstream crash unrelated to this project (golang/go#75584 and related: `golang.org/x/tools/go/ssa` panics building the call graph for any module depending on `go-json-experiment/json`, which this project pulls in transitively). Finding and fixing this tooling immediately surfaced real, previously-unnoticed issues, not just a formality: the pinned Go toolchain (`1.25.0`) was missing several stdlib security fixes, and three dependencies (`google.golang.org/grpc`, `golang.org/x/text`, `github.com/klauspost/compress`) had known CVEs with patched versions already available. All fixed in this same change (see Fixed below); `govulncheck -scan package ./...` now reports zero vulnerabilities.
- Wildcard tables (`` `dataset.prefix*` `` with `_TABLE_SUFFIX`): a wildcard table path is expanded to every real standard table in that dataset whose name starts with the prefix (views/external tables excluded), materialized individually so the embedded query engine's own native wildcard support resolves the reference into a real `UNION ALL` with a computed `_TABLE_SUFFIX` column. `requirePartitionFilter` and partition pruning are evaluated correctly per matched shard. See [README: Wildcard Tables](README.md#wildcard-tables-table_-and-_table_suffix).
- Schema autodetect for load jobs (`configuration.load.autodetect`) and external tables (`externalDataConfiguration.autodetect`): `AVRO`/`PARQUET` read their own embedded schema exactly; `NEWLINE_DELIMITED_JSON`/`CSV` sample up to 500 rows, widen each column's observed type, and always report `NULLABLE`. CSV header detection follows real BigQuery's own documented signal and folds a detected header into `skipLeadingRows` automatically. Nested/repeated top-level values are rejected explicitly rather than guessed at. See [README: Schema Autodetect](README.md#schema-autodetect-ndjson--csv--avro--parquet).
- Streaming inserts (`tabledata.insertAll`): rows commit directly to the catalog through the same `WRITE_APPEND`/`CREATE_NEVER` primitive BigQuery Storage Write's `_default` stream already uses, with row encoding shared with `NEWLINE_DELIMITED_JSON` load so nested `RECORD`/`REPEATED` fields work end-to-end. `skipInvalidRows` and `ignoreUnknownValues` match BigQuery's real defaults, and `insertId` deduplication is real within a bounded 15-minute window. `templateSuffix` and inserting into a view or external table are rejected explicitly. See [README: Streaming Inserts](README.md#streaming-inserts-tabledatainsertall).
- Benchmarks: `make bench` (Go benchmarks against the real HTTP handler stack) and [`cmd/locaql-bench`](cmd/locaql-bench), a dependency-free REST client that drives identical workloads against any BigQuery-REST-compatible server for reproducible, hardware-independent results. See [`docs/benchmarks.md`](docs/benchmarks.md) for methodology and results: `sync_query_*` pays a per-query engine-analysis cost (~200ms on the reference hardware), streaming inserts are a job-free catalog write and dramatically faster, and concurrent-query throughput shows substantial serialization under load.

### Fixed
- A panic anywhere in a job's execution (query, load, extract, copy) no longer crashes the entire server process — `jobService.recoverJobPanic` contains it to that one job, which now fails explicitly instead. Discovered by the benchmark work above: the embedded engine's WASM bridge can panic with a memory-corruption-shaped error after enough cumulative query executions, even on Linux/WSL. This alone isn't complete — a related failure mode (a panic inside a Go runtime finalizer) can't be caught by any application-level `recover()` — so `cmd/locaql-supervisor` now also restarts the emulator process automatically on an unexpected exit, bounded by a sliding-window limit. Running via the supervisor (the Docker image's entrypoint), the service stays available through this failure mode. Embedded-engine connections are also now pooled and reused across queries (`internal/server/sql_engine_pool.go`) rather than opened fresh per query. The bare `locaql` binary, run directly without the supervisor, now has the same auto-restart protection available via `locaql start --self-restart` (see next entry). See [Known Divergences](KNOWN-DIVERGENCES.md) Blocking #3 and [`docs/benchmarks.md`](docs/benchmarks.md) for the full picture.
- `locaql start --self-restart`: the bare `locaql` binary, run directly instead of through `cmd/locaql-supervisor`, can now opt into the same crash-recycling protection for itself. It re-execs itself as a supervised child and restarts it automatically on an unexpected exit, bounded by `--self-restart-max-restarts`/`--self-restart-window`/`--self-restart-backoff` (same defaults as the supervisor's). The restart-loop logic itself moved into a shared package, `internal/procsupervisor`, used by both `cmd/locaql-supervisor` and this new flag. Off by default — a direct `locaql start` with no flags behaves exactly as before, so existing scripts/CI relying on its process/PID stay unaffected.
- Bumped the pinned Go toolchain from `1.25.0` to `1.25.12`, closing several stdlib CVEs fixed in the Go 1.25.1–1.25.3 point releases (`net/url`, `encoding/pem`, `crypto/tls`, `crypto/x509`, `net/http`) that `govulncheck` (added in this same change) surfaced immediately upon first use.
- Bumped `google.golang.org/grpc` `v1.82.0` → `v1.82.1` (GO-2026-6061: xDS RBAC authorization engine and HTTP/2 transport server), `golang.org/x/text` `v0.38.0` → `v0.39.0` (GO-2026-5970: infinite loop on invalid input), and `github.com/klauspost/compress` `v1.18.2` → `v1.18.7` (GO-2026-5841: out-of-bounds read in `s2`) — all three were known, already-patched CVEs found by the same first `govulncheck` run.

## [0.10.0] - 2026-08-07

### Added
- BigQuery table partitioning and clustering through REST and the official Python client: time-unit/ingestion-time and integer-range definitions, ordered clustering fields, mutable partition expiration, lazy expired-row removal, required partition filters for every partitioning mode, real `INFORMATION_SCHEMA.PARTITIONS`/`COLUMNS`/`TABLE_OPTIONS` metadata, and executable read-only `_PARTITIONTIME`/`_PARTITIONDATE` pseudocolumns hidden from `SELECT *` and preserved across persistent DML. Physical pruning, SQL `PARTITION BY` DDL and the clustering optimizer remain explicit limits.
- Persistent single-statement GoogleSQL DDL/DML for query jobs: `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `TRUNCATE TABLE`, `CREATE [OR REPLACE] TABLE [AS SELECT]` and `DROP TABLE`, with target-table serialization, optimistic catalog version checks, statement atomicity, query parameters, BigQuery-shaped DML statistics, and a pinned `google-cloud-bigquery 3.42.3` CI smoke.
- Official Python `Client.load_table_from_file` compatibility through BigQuery's real multipart and resumable upload protocols, including `308` range progress, idempotent chunk retries, empty files, real `LoadJob` polling/statistics, and a pinned SDK smoke test in CI. Direct uploads currently require an explicit schema and incomplete resumable sessions are process-local/in-memory; see `KNOWN-DIVERGENCES.md`.
- Official Google Cloud Storage media downloads at `/download/storage/v1/b/{bucket}/o/{object}?alt=media`, including URL-escaped nested names, absolute `mediaLink` resources, `HEAD`, byte ranges (`206`/`Content-Range`) and MD5 response hashes. A pinned `google-cloud-storage 3.13.1` smoke test now covers upload, full download and ranged download in CI; the existing `objects.get?alt=media` route remains compatible.
- Lossless scalar nullability across load, catalog, query, REST, extract and Storage APIs: `NULL`, empty string, zero and false no longer collapse. Nullable Avro uses unions, nullable Parquet uses optional fields, `REQUIRED` null/absence fails explicitly, and the official Python smoke verifies `(None, "", 0, False)` plus correct `COUNT` semantics.

### Fixed
- BigQuery REST query/table rows now encode `TIMESTAMP` scalars as Unix epoch microseconds, allowing official clients to deserialize them into timezone-aware datetime values. The partitioning smoke also uses execution-relative UTC dates so its expiration checks do not become flaky as fixed fixture dates age.
- Polling a pending mutating query no longer executes it before the job acquires its resource lock or causes it to run twice. Whole-reference backticks around same-project `project.dataset.table` are now stripped correctly, and `MERGE` affected-row counts are derived from the before/after row multiset when the embedded driver reports zero despite applying the mutation.
- Final `getQueryResults` responses no longer include `pageToken`. The official Python query `RowIterator` treated its presence as another page and could loop indefinitely even after receiving the last row; this was discovered by the new nullable E2E.

### Changed
- Releases now follow the same promotion path as the code: opening or updating a same-repository `feature/* -> dev` pull request prepares and commits the next SemVer section on that work branch, and the subsequent `dev -> main` merge tags that exact promotion commit and publishes it. The automation no longer creates `release/*` branches or a second release-only pull request, preserves the protection of `dev`/`main`, rejects overlapping untagged release batches, and can safely retry an existing tag/release on the same commit.

## [0.9.2] - 2026-08-06

### Fixed
- `tabledata.list` 404'd for every table when called through the official `google-cloud-bigquery` client's `list_rows()`/`Table.list_rows()` — the request lands at `GET .../datasets/{datasetId}/tables/{tableId}/data` (real BigQuery's actual REST shape), but the router only recognized a made-up `.../tabledata/{datasetId}/{tableId}/data` shape that no official client ever requests (only this project's own tests and bundled UI did). A schema fetched via `tables.get` for the very same table would succeed, making the 404 look like a data problem rather than a routing gap. Fixed by handling the real path shape explicitly; the old shape is kept working as an internal alias.
- A load job's row/byte counts were written flat under `statistics.outputRows`/`processedBytes` instead of nested under `statistics.load.outputRows`/`outputBytes`, which is what `LoadJob.output_rows`/`output_bytes` on the official client actually reads — so a client that submitted and awaited its own load job always saw `output_rows` as `None`, even though the count had been computed correctly server-side. `Table.num_rows`/`num_bytes` had the same problem one level up: `tables.get` never set `numRows`/`numBytes` at all, for any table, load-populated or not. Both are now populated for managed tables (external tables and views still omit them, matching real BigQuery, since neither materializes rows into storage the same way).
- `tabledata.list`'s pagination response always included a `pageToken` key, even on the final page, echoing the request's own start index. The official client's row iterator for this endpoint is configured to treat the mere *presence* of a `pageToken` key as "there is another page" (`next_token="pageToken"`, not `nextPageToken`, unlike most other list endpoints) — so `list_rows()` looped forever re-fetching the same last page instead of ever returning. `pageToken` (and the `nextPageToken` alias already relied on elsewhere) are now both omitted once there is nothing left to page through.

## Versioning and deprecation policy

LocaQL follows [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`, where `MAJOR` bumps on a breaking
REST/gRPC contract change or a removed capability, `MINOR` adds capability without breaking existing behavior, and
`PATCH` is a fix with no contract change. Because this is a compatibility-surface emulator, "breaking" is judged
against `capabilities/registry.yaml`'s documented contract, not internal implementation details.

A capability is never removed silently: dropping or narrowing one that was previously `supported`/`partial` requires
a `MAJOR` bump, an entry in this file's release notes explaining what changed and why, and (if a replacement exists)
a pointer to it. There is no fixed support window for old versions today — this is a single-maintainer, locally-run
tool, not a hosted service with an SLA — but every release remains tagged and buildable from source indefinitely, so
pinning to an older version is always a real option for a consumer who isn't ready to move.

## How releases are cut

The normal path is the same linear promotion used by the code; there are no `release/*` branches:

1. Open or update a same-repository `feature/*`, `fix/*`, `docs/*` or `chore/*` pull request into `dev`. `.github/workflows/prepare-release.yml` checks the single `[Unreleased]` section, determines the SemVer bump (`### Removed` or a `BREAKING` marker → major, `### Added` → minor, anything else → patch), dates it as the next version after the latest `vX.Y.Z` tag, and commits that bookkeeping back to the work branch. It never pushes directly to protected `dev`.
2. Wait for that preparation commit before approving and merging the work PR into `dev`, then open the `dev -> main` pull request. The workflow rejects a second untagged release batch, so promotions stay ordered and `dev` always receives both the code and its final release notes.
3. Review and merge `dev -> main`. `.github/workflows/auto-tag-release.yml` verifies that `[Unreleased]` is empty, reads the first dated SemVer section, tags the exact merge commit, and calls `.github/workflows/release.yml` directly. This explicit call is required because a tag pushed with the default `GITHUB_TOKEN` does not start another workflow run.
4. `release.yml` validates (`build`/`vet`/`test`/`-race`), then in parallel builds and pushes the multi-arch (`linux/amd64`+`linux/arm64`) GHCR image tagged `X.Y.Z`, `X.Y` and `latest`, and publishes the cross-compiled binaries plus CycloneDX SBOM in the GitHub Release. Re-running the same promotion is idempotent when its tag already points to the same commit.

Pushing a `vX.Y.Z` tag by hand (`git tag v0.9.0 && git push origin v0.9.0`) still works too — `release.yml` keeps its original `push: tags` trigger for anyone who wants to skip the PR entirely, e.g. for a one-off rebuild. The same `make build`/`make build-all`/`make docker-build` targets also still work locally for a manual/offline build (they read the version from `git describe` when `VERSION` isn't set explicitly).
