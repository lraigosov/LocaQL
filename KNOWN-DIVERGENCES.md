# Known Divergences from Real BigQuery

This catalog complements the [Current Scope Matrix](README.md#current-scope-matrix) and `capabilities/registry.yaml`. Those two sources answer "is X supported, partial, or unsupported"; this document answers "if it's partial or missing, how much does that actually matter for a typical local development workflow, and is there a workaround." It exists to satisfy the master plan's own closure bar (§42.10, Nivel B: "Divergencias conocidas publicadas por severidad") and follows the same rule as everything else in this project: every entry below is derived from `capabilities/registry.yaml`, README limitation notes already in prose, or behavior verified directly against the current code — nothing here is speculative.

## Severity levels

- **Blocking** — the behavior is silently wrong (returns a 200 with incorrect or fabricated data) rather than failing explicitly, or a core workflow has no real implementation behind it at all. No local workaround exists.
- **Significant** — the feature is real but a common variant is unsupported; it fails explicitly (not silently), and a workaround or scope reduction is usually possible.
- **Minor** — a narrow edge case, a codec/format gap, or a cosmetic difference unlikely to affect a typical local development workflow.
- **By design (non-goal)** — deliberately out of scope per [No objetivos](local-support/bigquery-local-platform-master-plan.md) — not a gap to close, ever.

## Resolved since this catalog was first published

- ~~There was no real GoogleSQL parser or executor behind query jobs~~ — **fixed in Sesión 73**: `jobs.insert`/`jobs.query`/`projects.queries` now execute against a real embedded GoogleSQL engine ([`github.com/goccy/googlesqlite`](https://github.com/goccy/googlesqlite), pure Go, no cgo), which materializes every table a query references into a fresh in-memory instance and runs the query for real — `WHERE`, column projection, `JOIN`, aggregation, `ORDER BY` and `LIMIT` are now genuine GoogleSQL semantics, not a regex-matched table dump with a fabricated fallback for anything else. See `rest.jobs.query` in `capabilities/registry.yaml` for the precise remaining gaps, carried into Significant/Minor below.
- ~~Views and Materialized Views were not a real resource~~ — **fixed in Sesión 75**: `tables.insert` accepts `view.query`/`materializedView.query`, validated and schema-derived by actually running the query through the real engine at creation time; every access (query `FROM`/`JOIN`, `tabledata.list`, `INFORMATION_SCHEMA.PARTITIONS`) re-executes the stored query live, including a view selecting from another view (cycle-guarded). `INFORMATION_SCHEMA.VIEWS`/`MATERIALIZED_VIEWS`/`TABLES.table_type` reflect real resources now. See `rest.tables.views` in `capabilities/registry.yaml` for the precise remaining gaps (no patch-based redefinition, materialized views aren't actually cached), carried into Significant/Minor below.
- ~~`schema.fields[].fields` (STRUCT/RECORD substructure) and `schema.fields[].mode` (NULLABLE/REQUIRED/REPEATED) were dropped to a flat model~~ — **fixed in Sesión 76**: `tableField` now models `Mode` and nested `Fields` for real; `tables.insert`/`patch` accept and store them, `INFORMATION_SCHEMA.COLUMNS`/`tables.get` render them recursively, and `tabledata.list`/query results emit BigQuery's actual nested cell shape (`{"v": {"f": [...]}}` for RECORD, `{"v": [...]}` for REPEATED) rather than a flattened string. See `rest.tables.nested_schema` in `capabilities/registry.yaml` for the precise remaining gaps (NEWLINE_DELIMITED_JSON only for real nested load/extract; CSV/AVRO/PARQUET reject nested fields explicitly), carried into Significant below.
- ~~Nested `STRUCT`/`ARRAY` result columns didn't get a BigQuery-shaped schema entry~~ — **fixed in Sesión 76** as part of the same nested-schema work: the query engine's result schema is now built recursively from the driver's real type descriptor into `RECORD`/`REPEATED` `tableField`s, not a flattened type-name string.
- ~~`NULL` and empty string collapsed to the same stored cell~~ — **fixed in Sesión 38**: an escaped, lossless internal tag now preserves top-level SQL `NULL` separately from `""`, numeric zero and `false` without breaking historical `[][]string` snapshots. The distinction survives NDJSON/Avro/Parquet load, catalog/copy, query materialization and scanning, `tabledata.list`/`getQueryResults`, extract and Storage Read/Write; Avro uses nullable unions and Parquet optional nodes. `REQUIRED` null/absence fails explicitly. Unit coverage plus pinned `google-cloud-bigquery 3.42.3` E2E verifies Python receives `(None, "", 0, False)` and SQL observes `COUNT(NULL)=0` versus `COUNT("")=1`.
- ~~DDL/DML query jobs executed in a disposable database and lost every catalog mutation~~ — **fixed in Sesión 39**: single-statement `INSERT`/`UPDATE`/`DELETE`/`MERGE`/`TRUNCATE TABLE`, `CREATE [OR REPLACE] TABLE [AS SELECT]` and `DROP TABLE` execute through the real GoogleSQL engine and commit atomically to the catalog with target-resource serialization plus optimistic version checks against concurrent REST writes. Polling cannot execute a pending mutation early/twice. Query jobs expose real `statementType`/`numDmlAffectedRows`/`dmlStats`, verified end-to-end with pinned `google-cloud-bigquery 3.42.3`. Multi-statement persistent transactions, `ALTER TABLE`, cross-project targets and base-table DML inside a session transaction remain explicit limits below.
- ~~`timePartitioning`, `rangePartitioning` and `clustering` were silently dropped~~ — **fixed in Sesiones 40–42**: REST creation/update paths now validate, persist, clone and render time-unit/ingestion-time and integer-range partition definitions, up to four clustering fields, `requirePartitionFilter` and time-partition expiration. Catalog writes preserve ingestion partition IDs; column/range partitions derive from real stored values; lazy expiration removes expired dated partitions; `INFORMATION_SCHEMA.PARTITIONS`/`COLUMNS`/`TABLE_OPTIONS` expose real metadata and row counts. `_PARTITIONTIME`/`_PARTITIONDATE` are executable, typed, hidden from `SELECT *`, read-only and usable by required filters plus persistent DML; exact partition IDs survive updates/deletes even for duplicate user rows. Pinned `google-cloud-bigquery 3.42.3` verifies metadata, typed pseudocolumn rows, wildcard behavior, DML and errors. Physical pruning/cost behavior, AST-grade analysis and SQL `PARTITION BY` DDL remain explicit Significant limits below.
- ~~Table discovery only scanned text after `FROM`/`JOIN`, so comma joins and some nested shapes missed sources~~ — **fixed in Sesión 46**: LocaQL now parses and recursively walks the complete GoogleSQL AST for table-path nodes, covering CTE bodies, nested subqueries, quoted paths and comma-separated joins while ignoring table-like text in literals/comments. A narrow regex fallback is retained only when parsing fails so googlesqlite can still produce the authoritative syntax result. Completed query statistics now count logical bytes from materialized source rows rather than result rows. Cross-project resolution, physical pruning and AST-grade partition-filter/projection semantics remain separate limits below.
- ~~Sessions and multi-statement transactions were not implemented at all~~ — **partially fixed in Sesión 79**: `createSession`/`connectionProperties` (`session_id`) are real on both `jobs.query` and `jobs.insert`, session-scoped `` `_SESSION`.<table> `` temporary tables persist across separate query jobs sharing a session, `BEGIN`/`COMMIT`/`ROLLBACK TRANSACTION` give the session's own temp tables real, verified atomic commit/rollback semantics, sessions idle-expire, and `INFORMATION_SCHEMA.SESSIONS_BY_USER` lists a caller's own sessions. See Blocking #1 below for the upstream engine limitations this design had to work around, and Significant below for the remaining scope: base-table DDL/DML is persistent in autocommit mode but rejected while a session transaction is open; only `` _SESSION.<table> `` qualified references and only the `CREATE TEMP TABLE ... AS SELECT` form are supported.
- ~~BigQuery Storage API was not implemented at all~~ — **fixed for both Read and Write, each with its own bounded scope.** Read (Sesión 81): `CreateReadSession`/`ReadRows` are real, over a real `google.cloud.bigquery.storage.v1.BigQueryRead` gRPC service (Google's own generated stubs, `cloud.google.com/go/bigquery/storage/apiv1/storagepb`) on a separate plaintext listener (`--storage-grpc-addr`, default `:9060`). Column projection and `row_restriction` are rendered as a real `SELECT ... WHERE ...` executed through the same GoogleSQL engine every other query uses. Write (Sesión 82, same listener): `CreateWriteStream`/`AppendRows`/`GetWriteStream`/`FinalizeWriteStream`/`BatchCommitWriteStreams` are real — rows arrive protobuf-encoded (the Write API's own wire format, never Avro/Arrow) and are decoded via real runtime protobuf reflection (`google.golang.org/protobuf/types/dynamicpb`), then appended to the real catalog (`_default`/COMMITTED streams immediately, PENDING streams buffered until an atomic `BatchCommitWriteStreams`), with real offset-based exactly-once semantics for explicit streams. See Significant below for the bounded scope of each side (confirmed with the user before building both).
- ~~`tabledata.insertAll` (streaming inserts) was not implemented~~ — **fixed**: `POST .../datasets/{datasetId}/tables/{tableId}/insertAll` commits rows straight to the catalog through the same `tableService.upsertCopyDestination` (`WRITE_APPEND`/`CREATE_NEVER`) primitive BigQuery Storage Write's `_default` stream already uses, and reuses `parseNDJSONRow` for row encoding, so nested `RECORD`/`REPEATED` fields work identically to `NEWLINE_DELIMITED_JSON` load rather than a second, divergent write path. `skipInvalidRows` and `ignoreUnknownValues` are both real, matching BigQuery's own default (an invalid or unknown-field row fails the whole request unless `skipInvalidRows=true`). See `rest.tabledata.insertAll` in `capabilities/registry.yaml` for the exact scope, and Significant below for the bounded `insertId` dedup window and the explicit `templateSuffix` rejection.
- ~~Wildcard tables (`` `dataset.prefix*` ``) were not supported~~ — **fixed**: a table path ending in `*` is expanded, before materialization, to every real standard table (views/external tables excluded) in that dataset whose name starts with the prefix; the embedded engine's own native wildcard support (`goccy/googlesqlite`) then resolves the reference into a real `UNION ALL` with a computed `_TABLE_SUFFIX` column, once those real tables exist in its materialized catalog. See `sql.wildcard_tables` in `capabilities/registry.yaml` and Minor below for the `SELECT *` column-visibility caveat.
- ~~No schema autodetect anywhere (load jobs, external tables)~~ — **fixed**: `externalDataConfiguration.autodetect`/`configuration.load.autodetect` sample the source to infer `schema.fields` when it's omitted. `AVRO`/`PARQUET` read their own embedded schema exactly rather than guessing (both formats are self-describing); `NEWLINE_DELIMITED_JSON`/`CSV` sample up to 500 rows, widen each column's observed scalar type, and always report `NULLABLE` (autodetect never infers `REQUIRED` from a sample). CSV header detection follows real BigQuery's own documented signal (row 1 looks like a label when the rest of its column widens to a real, non-`STRING` type) and folds a detected header into `skipLeadingRows` so the real row-reading pass never re-reads it as data. See `rest.tables.external.schema_autodetect`/`rest.jobs.load.schema_autodetect` in `capabilities/registry.yaml` and Significant below for the bounded scope (first-file-only sampling, nested/repeated values rejected explicitly, Avro/Parquet limited to the primitive types this project's own encode path already round-trips).
- ~~Constructing a `DATE` from a string literal was off by one day~~ — **fixed in Sesión 85, and re-characterized: this was never an unconditional upstream engine bug, it was an ambient-host-timezone bug.** Discovered while wiring up CI (`.github/workflows/ci.yml`): the dedicated regression test passed on every local run but failed on GitHub's UTC-configured Linux/Windows/macOS runners. Root-caused, not just patched around: `SELECT DATE '2026-01-01'` only mis-parsed to `2025-12-31` on a host machine configured with a negative UTC offset (verified: reproduces on this project's own WSL dev environment, set to `America/Bogota`, UTC-5; disappears entirely under `TZ=UTC`; disappears entirely by setting Go's `time.Local = time.UTC` programmatically, with no environment variable involved) — something in the embedded query engine's DATE-literal handling consults the process's ambient local timezone. Fixed at the source: `internal/server/server.go` now forces `time.Local = time.UTC` in an `init()`, consistent with this project's existing convention of always working in UTC for BigQuery's own UTC-native DATE/DATETIME/TIMESTAMP semantics — not a per-call workaround, a process-wide correction applied once. Verified full test suite (including race) green on the real, unmodified `America/Bogota` host afterward, with the regression test's assertion flipped from pinning the wrong value to asserting the correct one.
- ~~`jobs.insert` silently ignored a client-supplied `jobReference.jobId` and always assigned its own auto-generated one~~ — **fixed, found via multi-client conformance testing.** Real BigQuery honors a client-supplied `jobReference.jobId` exactly (a documented feature official client libraries rely on: they generate a job ID client-side, submit it, and poll `getQueryResults`/`jobs.get` using that same value afterward, trusting the server used it). This had never surfaced through the existing Python conformance coverage, but broke the official Node.js `@google-cloud/bigquery` client outright the first time it was exercised against LocaQL (`test/clients/node/persistent_ddl_dml.js`, new in this session): `createQueryJob` generated its own job ID, LocaQL substituted `job_N` instead, and the client's subsequent `getQueryResults` poll for its own ID got a real "job not found" 404. Fixed in `jobService.resolveJobIDLocked` (`internal/server/jobs_service.go`): a supplied `jobReference.jobId` is now validated against BigQuery's own character rules (letters, numbers, underscores, hyphens, ≤1024 chars) and used exactly if not already taken for that project; an invalid ID is rejected with `400`, a collision with `409 Already Exists` (the same `"duplicate"` convention already used for dataset/table conflicts) — distinct from the pre-existing `requestId`-based retry idempotency, which still returns the existing job successfully on a retried request rather than an error.
- ~~Job statistics (`totalSlotMs`, `processedBytes`, `outputRows`, and the same fields nested under `statistics.load`) were rendered as bare JSON numbers~~ — **fixed, found by the same round of multi-client conformance testing, this time by the official Go client.** Real BigQuery renders every int64 statistics field as a JSON string, not a number — a deliberate, long-standing convention across Google's REST APIs to avoid precision loss in JavaScript's `Number` type. Python's and Node's JSON parsing both happened to accept a bare number here too, so neither caught it; the official `cloud.google.com/go/bigquery` client's generated structs use a `,string` json tag that rejects an unquoted number outright (`"json: invalid use of ,string struct tag, trying to unmarshal unquoted value into int64"`), failing on the very first job status poll (`test/clients/go/persistent_ddl_dml.go`, new in this session). Fixed in `renderJobResource` (`internal/server/jobs_service.go`) by rendering these fields with `strconv.FormatInt` like the already-correct `numDmlAffectedRows`/`totalBytesProcessed`/`numRows`/`numBytes` fields elsewhere in the same response.
- ~~Table/query result schema fields rendered their type using GoogleSQL/standard-SQL names (`INT64`, `BOOL`, `STRUCT`) instead of BigQuery's REST wire names (`INTEGER`, `BOOLEAN`, `RECORD`)~~ — **fixed, found by the same Go client conformance run.** Both forms are documented, accepted aliases of the same `TableFieldSchema.type` per BigQuery's own API reference, and the official Go client's own *schema* parser recognizes both — but its separate *row-value* converter (`convertBasicType`) switches only on the resolved legacy names and rejected `INT64` outright (`"unrecognized type: INT64"`) the first time it read an actual query result row, even though the schema itself parsed fine. `tableField.Type` remains GoogleSQL-named internally (needed as-is to build real `CREATE TABLE` statements against the embedded engine — see `realSQLScalarTypes` in `sql_engine.go`), but `renderTableSchemaFields` (`internal/server/bigquery.go`) now maps to the legacy name (`restFieldTypeName`) only at the REST-response boundary. `INFORMATION_SCHEMA.COLUMNS.data_type` is deliberately unaffected — real BigQuery renders that column using GoogleSQL type names, the opposite convention, in that specific context only.
- ~~A job resource never echoed back the submitted query text (`configuration.query.query` was always empty)~~ — **fixed, found by official Java client conformance testing.** Real BigQuery always includes the original query text in a job resource. Python's and Node's client models don't require it to be present to keep working, so this went unnoticed; the official `com.google.cloud:google-cloud-bigquery` client's `QueryJobConfiguration.fromPb` (used to reconstruct a `Job` object from the `jobs.insert` REST response) requires it non-null and threw a bare `NullPointerException` via `Preconditions.checkNotNull` on the very first call (`test/clients/java/.../PersistentDdlDml.java`, new in this session), before the job had even run. Fixed in `renderJobResource` (`internal/server/jobs_service.go`) by including `j.QueryText` in `configuration.query.query` alongside `priority`.
- ~~A `Content-Encoding: gzip` request body was never decompressed, and the resulting JSON-parse failure was silently treated as "the field was omitted" rather than a hard error~~ — **fixed, found by the same Java client conformance run, and the most consequential of the four multi-client findings.** The official Java client (`google-http-client`) gzip-compresses `POST`/`PUT` bodies above a size threshold by default — a real, standard behavior, not a test artifact. Every handler's `io.ReadAll(r.Body)` + `json.Unmarshal` read raw gzip bytes, which fail to parse as JSON; because that parse failure was already handled defensively (treating malformed/absent fields as "just not provided" rather than always erroring), a gzip-compressed `jobs.insert` silently created a real job with an *empty query string* and default `jobType` instead of either running the real statement or failing loudly — worse than an error, since the job still reported `DONE` with no error and a placeholder simulated result (`"query job executed"`), masking the fact that nothing had actually run. Fixed centrally, not per-handler: a new `withGzipRequestDecoding` middleware (`internal/server/server.go`) transparently decompresses any incoming request whose `Content-Encoding` is `gzip` before any handler reads the body, covering every current and future REST endpoint in one place rather than patching individual `io.ReadAll` call sites.
- ~~The official `bq` CLI could not connect to LocaQL at all~~ — **fixed.** Unlike every other official client library (Python, Node.js, Go, Java), `bq` is built on the older `apitools`/Discovery-API-driven generator: before issuing any real API call it fetches a discovery document (`GET /$discovery/rest?version=v2`) describing the entire API surface, which LocaQL never served. `internal/server/discovery.go` now serves a hand-written discovery document (`internal/server/assets/bigquery_discovery_v2.json`), deliberately scoped to the `jobs.*` resource only (`insert`/`get`/`list`/`query`/`getQueryResults`/`cancel`) — real BigQuery's actual discovery document is ~570KB describing the entire API; writing LocaQL's own version, covering only what it actually implements, was a deliberate choice consistent with this project's capability-transparency philosophy rather than bundling and relabeling Google's document. `rootUrl`/`baseUrl`/`mtlsRootUrl` are rewritten to the request's own `Host` at serve time so `bq`'s subsequent calls come back to LocaQL rather than real Google infrastructure. This makes `bq query` (including real persistent DDL/DML — verified with the same CREATE/INSERT/UPDATE/MERGE/DELETE/SELECT sequence every other client's conformance test runs, `test/clients/bq/persistent_ddl_dml.sh`), `bq show -j`, `bq cancel` and `bq ls -j` work; `bq` subcommands depending on datasets/tables/tabledata resources (`mk`, `ls` for datasets/tables, `load`, `extract`, `cp`, `insert`) are not yet supported, since those resources aren't described in the document — see `rest.discovery_document` in `capabilities/registry.yaml`. Separately, `bq` refuses to run at all without a locally "active account" configured, even though it never validates a token against an anonymous-only local server: `CLOUDSDK_AUTH_ACCESS_TOKEN` supplies a literal bearer token bq attaches to its requests without any real validation, which is the mechanism the conformance test and CI job both use.

## Blocking

### 1. The query engine's own `CREATE TEMP TABLE` and `ROLLBACK` are unusable (upstream engine limitations)

Verified directly against the real query engine with a disposable spike (deleted after use, findings preserved here), while building session support in Sesión 79:

- **`CREATE TEMP TABLE` registration does not survive past the single `Exec`/`Query` call that created it** — not even when explicitly pinned to one `*sql.Conn` (bypassing `database/sql`'s connection pool entirely), not even wrapped in an explicit, still-open `BEGIN`/`COMMIT` pair spanning the calls. A temp table created in one call is reported as "Table not found" by the very next call on the exact same connection. Ordinary (non-temp) tables created via `CREATE TABLE`/`CREATE SCHEMA` are unaffected and persist correctly across separate calls — this is specific to `TEMP`/`TEMPORARY` table registration.
- **`ROLLBACK`/`ROLLBACK TRANSACTION` fails unconditionally** with `Statement not supported: RollbackStatement` — reproduced with and without the `TRANSACTION` keyword, and regardless of whether a transaction was actually open. `BEGIN`/`BEGIN TRANSACTION`/`COMMIT`/`COMMIT TRANSACTION`/`START TRANSACTION` are all accepted without error, but since `ROLLBACK` can never succeed, the engine's own transaction statements cannot deliver real, usable atomicity as-is.

### 2. The query engine does not work when run natively on Windows or macOS (only verified on Linux/WSL)

Discovered in Sesión 85 while wiring up CI's `native` job (`windows-latest`/`macos-latest` GitHub Actions runners) — the first time this project's test suite has ever actually executed on native Windows or macOS; every prior session's validation ran through WSL/Linux exclusively (see `CONTRIBUTING.md`), so this gap existed from the moment the real query engine (`goccy/googlesqlite`) was adopted in Sesión 73 but was never observed until now. `go build`/`go vet` succeed on both platforms (and cross-compiling *for* windows/darwin targets from Linux, see `cross-build` in `.github/workflows/ci.yml`, also succeeds — the binary links fine), but any code path that actually runs a query fails at analyzer initialization: `failed to create analyzer: failed to initialize analyzer options: wasm trap: invalid memory address or nil pointer dereference`. This affects every query-executing test (`jobs.query`, views, the Storage Read/Write API, sessions — anything that reaches the engine) on both `windows-latest` and `macos-latest`.

**Investigated further in Sesión 85 (bounded — see below for why it stopped there):** the "wasm trap" wording is not a runtime WASM VM (no `wazero`/`wasmer`/`wasmtime` dependency exists anywhere in `go.sum`, checked directly). It comes from `github.com/goccy/googlesqlwasm2go`, which transpiles a WASM build of the real ZetaSQL/GoogleSQL analyzer (C++) into a single **316,921-line generated Go source file** (`wasm2go.go`) ahead of time, and wraps calls with `recover()` to turn a Go-level panic (an out-of-bounds access into the transpiled module's emulated linear memory, represented as a Go `[]byte`) into an `error` shaped like a real WASM trap message — `newAnalyzerOptions()` (`goccy/googlesqlite/internal/analyzer.go`) calls into this transpiled code via `googlesql.NewLanguageOptions()`/`googlesql.NewAnalyzerOptions2()`, and the panic happens somewhere inside that 316k-line file, on native Windows/macOS only. No existing upstream issue was found for this in `goccy/googlesqlite` or `goccy/googlesqlwasm2go` (searched via GitHub's issue search API). Stopped here rather than going further: a 316,921-line machine-generated file with no hand-written structure to reason about isn't practically debuggable by reading it, and reproducing/bisecting the actual OS-specific memory-layout difference that trips this would need purpose-built tooling (e.g. a debug build of the transpiler itself) that doesn't exist yet — a realistic fix is upstream work, not a LocaQL-side patch. **Workaround: none from LocaQL's side today; run and test LocaQL through WSL on Windows, and (unverified) presumably needs the same on macOS.** `.github/workflows/ci.yml`'s `native` job marks its `go test ./...` step `continue-on-error: true` because of this — `go build`/`go vet` still block on failure, only the known-broken runtime behavior doesn't fail the PR.

### 3. The embedded engine's WASM bridge can crash the whole process under sustained load, even on Linux/WSL (the officially supported platform) — distinct from Blocking #2

Discovered while building this project's own comparative benchmark suite ([`docs/benchmarks.md`](docs/benchmarks.md)), running real, repeated query load against a single long-lived LocaQL process on Linux/WSL — not native Windows/macOS, and not a one-off: reproduced twice in the same session.

- **First failure mode (contained):** `database/sql.Open("googlesqlite", ...)` itself — the call that materializes a fresh isolated engine instance for one query — panics with a memory-corruption-shaped `runtime error: slice bounds out of range [-21...:]`, from inside `goccy/go-googlesql`'s `NewSimpleCatalog`/`invoke`, after roughly 250-350 cumulative `sql.Open` calls over the process's lifetime in our testing (not a fixed, deterministic count). This is **not** the analyzer-initialization trap of Blocking #2 — it happens deep inside catalog construction, on Linux, and reproduces without ever touching Windows/macOS. `jobService.recoverJobPanic` (`internal/server/jobs_service.go`) now catches this at the job-executor goroutine boundary and fails only that one job — verified with a dedicated regression test (`internal/server/panic_recovery_test.go`) and confirmed live: two such panics were caught in the same benchmark run, and the server kept serving requests immediately afterward.
- **Second failure mode (not contained, no mitigation available):** continuing the same load past that point, the process still crashed fatally — this time from a panic inside a **Go runtime finalizer** (`runtime.runFinalizers` → `(*SimpleCatalog).free`, itself calling back into the same fragile WASM bridge). A finalizer runs on a dedicated Go-runtime-managed goroutine that is never part of any request's call stack, so no `defer`/`recover` anywhere in this project's own code — or any Go application's code — can reach it. This is the same underlying WASM memory corruption, just surfacing at garbage-collection time instead of at query-execution time.

**Not fixable at the root from this project's own code** (the bug lives in `goccy/go-googlesql`'s WASM memory management), so the mitigation here is defense in depth rather than a fix: `jobService.recoverJobPanic` contains a panic during query execution to that one job instead of the whole process; `internal/server/sql_engine_pool.go` reuses embedded-engine connections across queries (measured to reduce `sql.Open` call volume, though not to prevent the crash outright — the corruption reproduces at roughly the same cumulative query count regardless, pointing to shared state inside the WASM bridge rather than something scoped per connection); and process-level auto-restart on an unexpected exit, bounded by a sliding-window limit so an unrelated, persistent problem still fails loudly instead of crash-looping forever (shared implementation in `internal/procsupervisor`). That auto-restart is available two ways: `cmd/locaql-supervisor` (the Docker image's entrypoint) always applies it to the emulator process it manages, and the bare `locaql` binary can opt into the same protection for itself via `locaql start --self-restart`, which re-execs itself as a supervised child instead of running the server in that same process directly. Net effect: running via `locaql-supervisor`, or running `locaql start --self-restart` directly, the service stays available through this failure mode — the process recycles instead of the deployment going down. Running the bare `locaql start` without `--self-restart` (the default, unchanged for backward compatibility) still has no such protection. See `docs/benchmarks.md` for the full reproduction and measurements.

**Status as of v0.12.0:** all four mitigations above have shipped. `.github/workflows/soak-test.yml` (manual `workflow_dispatch`, since it deliberately sustains load for minutes rather than seconds) drives `cmd/locaql-bench --soak-duration` against a `locaql start --self-restart` process to validate the restart loop over many cycles instead of only the 2-3 reproduced manually while building it — it does not require the crash to actually occur to pass (the crash itself remains non-deterministic; a given soak run may see zero, one, or several occurrences), only that the server recovers within a bounded outage window (`--soak-max-outage`) every time it does. **The upstream root cause itself is still unresolved** — this is a mitigation posture, not a fix, and is not expected to change without a fix inside `goccy/go-googlesql` itself.

Neither limitation is workaroundable from LocaQL's side by passing different SQL text — both are hard failures/no-ops inside the engine's own analyzer, not a binding or query-construction issue on LocaQL's end (both a bare `?` and various literal forms were tried). **Consequence for this project:** session-scoped temporary tables and `BEGIN`/`COMMIT`/`ROLLBACK TRANSACTION` are implemented entirely in LocaQL's own code instead — a session's temp tables live in LocaQL's own catalog (`sessionRecord.TempTables`, materialized into a fresh engine instance per query as needed, the same architecture already used for every other table) and are snapshotted/restored by LocaQL itself for commit/rollback, never passed through to the engine's native `TEMP TABLE`/`ROLLBACK` statements. See `rest.jobs.query` (sessions) in `capabilities/registry.yaml` and the [Sessions and Multi-Statement Transactions](README.md#sessions-and-multi-statement-transactions) README section for the resulting design.

## Significant

- **Partition pruning and cost reduction cover only an AST-proven read-only equality subset; clustering still does not reorder/optimize storage.** With one physical occurrence of a partitioned table, `partition_column = typed_literal` (including `_PARTITIONDATE`/`_PARTITIONTIME`, optionally inside `AND`) materializes only the matching time/ingestion partition or entire integer bucket and reduces logical `totalBytesProcessed`. `OR`, parameters, casts/functions, inequality/range predicates, repeated references and ambiguous forms retain the full table. DDL/DML deliberately never prune because their atomic final-image commit must preserve untouched partitions. This is logical row pruning, not physical column bytes or BigQuery billing parity. `requirePartitionFilter` now uses AST filter identifiers and ignores literals/comments; direct-pseudocolumn projection recognition remains lexical.
- **Partitioned/clustering table creation is REST/SDK-only.** The persistent DDL subset does not parse or persist GoogleSQL `PARTITION BY`/`CLUSTER BY` clauses yet. Hive/external partitioning remains separately unsupported.
- **Views can't be redefined after creation.** `tables.patch`/`tables.update` don't support changing an existing view's `query` — the same "patching X after creation isn't supported" limitation already declared for external tables' `externalDataConfiguration`.
- **Materialized views aren't actually materialized/cached.** A `MATERIALIZED_VIEW` is recomputed live on every access exactly like a plain `VIEW` — real BigQuery's periodic background refresh, `enableRefresh`/`refreshIntervalMs`/`lastRefreshTime` semantics are not modeled. This is a declared simplification, not a faked cache: the `type` and `INFORMATION_SCHEMA.MATERIALIZED_VIEWS` entry are real, but there is no actual materialization step to speed up repeated access.
- **A 3-part `project.dataset.table` reference only resolves against the request's own project.** The real query engine models one SQL schema per dataset with no project-level concept; a reference is only rewritten to `dataset.table` when its leading component case-insensitively matches the request's `projectID` (`internal/server/sql_engine.go:stripProjectPrefix`). A genuine cross-project query fails with "table not found" rather than silently resolving against the wrong project or being supported.
- **`RECORD`/`REPEATED` schema fields are only really supported end-to-end for `NEWLINE_DELIMITED_JSON`.** Load, extract and external tables all reject a schema containing a `RECORD`/`STRUCT` type or a `REPEATED` mode explicitly for `CSV`, `AVRO` and `PARQUET` (`rejectNestedFields`) rather than silently flattening, corrupting, or truncating the data. CSV never will support this (matching real BigQuery — CSV has no nested representation); Avro and Parquet could in principle (both formats have native nested/repeated types) but that is deferred, not attempted.
- **Column evolution (`tables.patch` with `schema`) only allows additive/relaxing changes.** Appending new (`NULLABLE`-only) columns and relaxing `REQUIRED` to `NULLABLE` are supported; removing a column, renaming/reordering one, changing its type, or tightening `NULLABLE` to `REQUIRED` are all rejected explicitly. There is no support for evolving a nested `RECORD` field's own sub-`fields` after creation.
- **Direct BigQuery file uploads are supported, but resumable sessions are local-process state.** The official Python client's `load_table_from_file` now works through both multipart and resumable protocols, including real `308`/`Range` progress and `LoadJob` polling. Unlike BigQuery's durable upload service, an incomplete LocaQL resumable session is buffered in server memory, expires after one idle hour, and is lost on restart; it is not spooled to disk and has no production-scale upload quota model. Completed sessions/jobs release the uploaded bytes immediately. Together with the explicit-schema requirement above, this makes the feature appropriate for bounded local integration fixtures rather than arbitrary warehouse-scale files.
- **No `maxBadRecords`/per-row error tolerance** in load jobs: any malformed row fails the whole job.
- **Schema autodetect samples only the first `sourceUri`** (a multi-file load/external table with divergent columns across files should provide `schema.fields` explicitly); NDJSON/CSV inference is capped at a 500-row sample and never infers `REQUIRED`, only `NULLABLE`; a top-level nested/repeated (`RECORD`/`ARRAY`) value in any format is rejected explicitly rather than guessed at; Avro/Parquet autodetect only recognizes a bare primitive or a two-branch `["null", primitive]` union, matching this project's own Avro/Parquet encode scope (`INT64`/`FLOAT64`/`BOOL`/`STRING`) rather than the full type systems of those formats.
- **ORC is unsupported** for load/extract/external tables — evaluated and explicitly deferred (both available Go libraries failed a reliability bar the project already applies to Parquet; see master plan §11.3), not silently ignored.
- **Snapshot, clone and time travel are not implemented** (`FOR SYSTEM_TIME AS OF` and friends) — no table versioning exists yet.
- **Session temp tables must be referenced fully qualified as `` _SESSION.<table> ``; a bare unqualified name is not resolved against the session.** AST discovery deliberately materializes only two- or three-part physical paths; real BigQuery additionally lets a session query resolve its own temp table by bare name. Narrower than real BigQuery, but explicit and consistent with how catalog table references work in this project.
- **Only `CREATE TEMP TABLE <name> AS <select>` is supported for creating a session temp table** — the separate two-statement form (`CREATE TEMP TABLE <name> (schema...)` followed by standalone `INSERT INTO` statements) is not implemented. Persistent DML targeting `_SESSION` fails explicitly rather than being mistaken for base-table DML. Real BigQuery supports both forms.
- **A session transaction's atomicity only covers that session's own temp tables**, never real base tables. Persistent base-table DDL/DML works in autocommit query jobs, but attempting it while a session transaction is open fails explicitly; this prevents `ROLLBACK` from pretending to undo a catalog write it did not govern. Multi-statement persistent transactions remain unimplemented.
- **Persistent DDL/DML is a bounded single-statement subset.** Implemented: INSERT/UPDATE/DELETE/MERGE/TRUNCATE, CREATE TABLE/CTAS/CREATE OR REPLACE and DROP, including query parameters and affected-row statistics. Not implemented: `ALTER TABLE`, procedural SQL, atomic persistent multi-statement scripts, cross-project mutation targets, or DML against views/external tables. These variants fail explicitly rather than returning success with discarded effects.
- **`INFORMATION_SCHEMA.SESSIONS_BY_PROJECT` is not implemented** (only `SESSIONS_BY_USER`) — this matches real BigQuery, which also has no `SESSIONS_BY_PROJECT` view (sessions are inherently scoped to the user/connection that created them), so this is full fidelity, not a gap.
- **A session's idle-expiration is lazily purged on next access, not swept in the background** — an idle-expired session simply reports "not found" the next time anything tries to use it (same convention already established for table expiration); there is no `INFORMATION_SCHEMA.SESSIONS_BY_USER` row for one already past its idle timeout, but nothing proactively frees its underlying resources the instant it goes idle either.
- **BigQuery Storage Write API only supports COMMITTED and PENDING streams — BUFFERED and `FlushRows` are unimplemented.** `CreateWriteStream`/`AppendRows`/`GetWriteStream`/`FinalizeWriteStream`/`BatchCommitWriteStreams` are real: the `_default` stream and explicit COMMITTED streams append to the real catalog immediately; explicit PENDING streams buffer in server memory until `BatchCommitWriteStreams` applies every named, finalized stream's rows to the catalog in one atomic call. Requesting a `BUFFERED` stream returns an explicit `Unimplemented` status at `CreateWriteStream` (not silently downgraded to COMMITTED); `FlushRows` is likewise `Unimplemented` (it only ever applies to BUFFERED streams, which don't exist here).
- **A proto row field that is `repeated` or a nested message is rejected per-row, not silently flattened or corrupted.** `AppendRows` decodes each row via real runtime protobuf reflection (`dynamicpb`) matched to the destination table's columns by name; a field with `Cardinality() == Repeated` or `Kind() == MessageKind/GroupKind` produces a `RowError` for that specific row (the request's other rows still succeed) rather than guessing at a flattening. A destination table with a `RECORD`/`REPEATED` schema field is rejected even earlier, at `CreateWriteStream` (or the first append to `_default`), reusing the same `rejectNestedFields` convention already used by CSV/AVRO/PARQUET load/extract.
- **`missing_value_interpretations` and mid-stream schema updates (`AppendRowsResponse.updated_schema`) are not implemented.** A nullable field absent from a proto row is SQL `NULL` and an absent `REQUIRED` field is a row error, regardless of any alternate missing-value interpretation the client requests; the destination schema is read once and never re-checked mid-stream.
- **BigQuery Storage Read API only supports Avro framing, one stream per session, and no `SplitReadStream`.** `CreateReadSession`/`ReadRows` are real (a separate plaintext gRPC listener, `--storage-grpc-addr`, default `:9060`; column projection and `row_restriction` become a genuine `SELECT ... WHERE ...` run through the same real GoogleSQL engine every other query uses — not a hand-rolled filter). Requesting Arrow framing (`arrow_serialization_options`) returns an explicit `Unimplemented` status rather than silently ignoring it or producing wrong bytes. Every session returns exactly one stream regardless of `max_stream_count`/`preferred_min_stream_count`; `SplitReadStream` returns `Unimplemented` explicitly — there is nothing to split since there's only ever one stream. A table with a `RECORD`/`REPEATED` field is rejected explicitly at `CreateReadSession` (same `rejectNestedFields` convention already used by CSV/AVRO/PARQUET load/extract). Sessions never expire (real BigQuery auto-expires them after 6 hours) — not a concern in a local, single-process emulator with no session cleanup pressure.
- **`GET /_emulator/metrics` is plain JSON, not Prometheus text exposition format.** Consistent with the rest of this REST API and adds no new dependency, but means a real Prometheus/Grafana instance can't scrape it directly without an intermediate exporter translating the JSON shape. There is also no distributed tracing (a request's path through REST handler → service → SQL engine → SQLite is not span-instrumented), no OpenTelemetry export, no slow-query log, and no sensitive-data log redaction policy — this is the "minimal metrics" half of the master plan's broader Fase quince observability vision, not the full wishlist. Separately: there is no automatic retry mechanism anywhere in this codebase (a failed job is never re-run), so no retry counter is reported in the metrics snapshot — reporting one would always read zero.
- **`GET /_emulator/diagnostics` (Sesión 83) does not audit the dataset/table/routine/model catalog, and cannot report whether the Storage API gRPC listener is actually reachable.** It aggregates persistence write health, the actual recent job failures (not just a count), which specific resource keys are currently locked, active session count, and the `LOCAQL_*` environment variables actually in effect — but a catalog-wide count/audit is a separate, larger feature not attempted here, and the gRPC listener lives in a separate process concern (`cmd/locaql/main.go`) with no shared state back into `internal/server` today, so its reachability can't be reported from this endpoint. No fault-injection capability exists either.
- **A distributed release binary (`make build-all`'s `dist/<os>_<arch>/locaql`, or any cross-compiled binary run outside the repo) does not locate `capabilities/registry.yaml` unless launched with that relative path still resolvable, or `--capabilities` pointing at an explicit path.** `cmd/locaql/main.go`'s `start`/`capabilities` subcommands default `--capabilities` to the literal relative path `capabilities/registry.yaml`; this was only ever exercised in development where the process's working directory is the repo root. The Dockerfile works around this by setting `WORKDIR /etc/locaql` and copying the registry to `/etc/locaql/capabilities/registry.yaml` so the default relative path still resolves inside the container — but a bare `dist/linux_amd64/locaql` binary copied elsewhere and run from an arbitrary directory needs `--capabilities /path/to/registry.yaml` passed explicitly. Not a bug in the emulator's request-handling logic — found empirically while cross-compiling the Windows e2e test binary for the release-pipeline verification (Sesión 84): running it from a directory whose relative `../../capabilities/registry.yaml` didn't resolve reproduced the exact same "capabilities registry path" not-found failure a misplaced release binary would hit.
- **`copy` jobs cover only the basic single-source case** — multi-source copy, extended write dispositions and cross-location semantics are not covered.
- **`routines` has no full `update` (PUT)** — only partial `patch`.
- **`tabledata.insertAll` deduplicates `insertId` within a bounded 15-minute window per table, not BigQuery's own undocumented, effectively-unbounded best-effort window** — the same explicit-TTL trade-off already made for job `requestId` idempotency, applied here for consistency rather than trying to reverse-engineer real BigQuery's unpublished retention. `templateSuffix` (create-and-write to a templated shard table) is rejected explicitly with a 400 rather than silently ignored; unknown top-level JSON fields are detected, but a field nested inside a `RECORD` value is not separately checked against that record's own sub-schema for `ignoreUnknownValues` purposes.

## Minor

- Compression codec sets are intentionally partial per format (see the tables in the [Load Jobs](README.md#load-jobs-real-row-ingestion-ndjson--csv--avro--parquet) and [Extract Jobs](README.md#extract-jobs-real-table-export-ndjson--csv--avro--parquet) sections) — e.g. no `ZSTD`/`BROTLI`/`LZ4RAW` for Parquet extract; load never accepts a non-`NONE` compression value for Avro/Parquet, since their codec is embedded in the file.
- External tables: no Hive partitioning, no patching `externalDataConfiguration` after creation, no compression option. (Autodetect is real now — see `rest.tables.external.schema_autodetect`.)
- Wildcard tables: `SELECT *` against a `` `dataset.prefix*` `` reference includes `_TABLE_SUFFIX` as a real column instead of hiding it as BigQuery's own pseudocolumn does — an embedded-engine-level behavior, not currently post-processed around. Select `_TABLE_SUFFIX` explicitly if this matters for a given query.
- Fake GCS JSON API: no resumable object uploads, IAM/ACLs, object versioning, lifecycle rules, notifications, or signed URLs. Full and ranged downloads are implemented on the official `/download/storage/v1/...` route and verified with pinned `google-cloud-storage 3.13.1`; the older `?alt=media` route remains an alias. Separately, the Go `cloud.google.com/go/storage` client's `NewReader` has an open upstream P1 bug (`googleapis/google-cloud-go#1619`) that ignores `STORAGE_EMULATOR_HOST`; this prevents using that one Go method as evidence but is not a server limitation.
- `INFORMATION_SCHEMA.TABLE_STORAGE` and region qualification/validation are not implemented.
- `INFORMATION_SCHEMA.X` queries don't support column projection: `SELECT table_name, table_type FROM ...INFORMATION_SCHEMA.TABLES` still returns every column of that builder's fixed schema (`table_catalog`, `table_schema`, `table_name`, `table_type`), ignoring the requested column list — found while testing the new Views feature against `INFORMATION_SCHEMA.TABLES`. Unrelated to views specifically; every `INFORMATION_SCHEMA` builder works this way.
- `jobs.list` has base pagination only; full filter/order parity (already partially there: `stateFilter`/`userEmail`/`allUsers`/`parentJobId`/time range) and pagination for `routines`/`models` listings are incomplete.
- Multi-shard extract splitting (`LOCAQL_EXTRACT_SHARD_MAX_BYTES`) only applies to local-path destinations; the `gs://`/fake-GCS mapping doesn't get its own size-based split beyond that.
- Several capabilities are marked `partial` in the registry purely because they are local-only conveniences with no distributed-BigQuery equivalent to compare against (job persistence across restart, configurable worker/backpressure limits, per-resource mutation serialization, atomic catalog snapshot) — these aren't gaps so much as "there's nothing on the real-BigQuery side to be at parity with."
- `requestId` idempotency uses a TTL-bounded replay window rather than BigQuery's full retention semantics.
- Registry test citations under the `conformance/foundation/...` and `conformance/pagination/...` naming scheme predate the current, much smaller `test/conformance/cases/foundation.yaml` (3 cases: health/version/capabilities) and `pagination.yaml` — several of those citations don't correspond to a locatable conformance case today. The real coverage for those capabilities exists as `unit/server/...` tests instead; the citations themselves are stale pointers, not evidence the behavior is untested. Left as-is here since re-auditing every citation across the registry is a separate, smaller cleanup, not part of this catalog.
- **`queryParameters` (Sesión 86) only bind scalar types, and two of those scalars have their own narrower limits.** `ARRAY`/`STRUCT` parameter types are rejected explicitly with a 400 (out of scope for this increment, the same complexity class as nested schema handling elsewhere). `NUMERIC`/`BIGNUMERIC` parameter types are also rejected explicitly — not merely deferred, but empirically confirmed unfixable without SQL rewriting: the driver infers a bound value's GoogleSQL type from its own Go type, and a Go `string` (there's no native Go decimal type) always infers as `STRING` rather than `NUMERIC`/`BIGNUMERIC` in an arithmetic or comparison context; the actual fix (`CAST(@a AS NUMERIC)`) would require rewriting the client's own SQL text to inject a `CAST` around every parameter reference, i.e. parsing arbitrary client SQL, which this project deliberately avoids. A completely context-free `NULL`-valued parameter with nothing around it to infer a type from (e.g. a bare `SELECT @a AS x` with no comparison or arithmetic) defaults to `INT64` in the reported result schema — the same default-typing behavior already documented above for a bare `?` inside a hand-built `ARRAY`/`STRUCT` literal, not a new category of gap. Multi-statement script jobs (`isScript=true`) don't thread `queryParameters` to their per-statement child jobs yet.

## By design (non-goal)

Not divergences to close — explicitly out of scope per [No objetivos](local-support/bigquery-local-platform-master-plan.md):

- IAM, row access policies, policy tags, and any local security/authorization model. The emulator is anonymous-only, permanently.
- Slots, reservations, autoscaling, and real billing/cost estimation.
- Dremel-level distributed performance, latency or scalability parity.
- An exact visual clone of Google Cloud Console.
- `GEOGRAPHY`, `RANGE`, `INTERVAL`, `JSON` as query engine scalar types — deferred explicitly before the core-scalars work started (Sesión 77), reconfirmed in Sesión 86: none of these are wired into `realSQLScalarTypes` (`internal/server/sql_engine.go`), load/extract schemas, or query parameter types (see Significant below). Not attempted, not a discovered gap.
